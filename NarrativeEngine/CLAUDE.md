# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

**ChronosTUI** is a terminal-based RPG narrative engine that bridges deterministic game-state management with LLM-driven storytelling. The player explores Elowen, a dark fantasy world built on the ruins of the Eternal Aurelian Empire, and every narrative response is generated by an LLM that also proposes typed state mutations applied by the engine.

For the design rationale ("why we built it this way" — memory model, op contract, persistence decisions, deferred work), see `documentation.md`. This file is the operational reference; `documentation.md` is the narrative design doc.

## Setup & Running

```bash
pip install -r requirements.txt

# .env
GITHUB_TOKEN=<your_github_token>
LLM_MODEL=gpt-4o-mini   # optional; must support response_format=json_object

python main.py
```

The AI backend is **GitHub Models** (`https://models.inference.ai.azure.com`). `python-dotenv` loads `.env` automatically.

## Turn Loop (the central flow)

Every player input goes through this pipeline:

1. **TUI** (`ui/app.py`) captures input, increments `turn_count`, appends `PLAYER:` log line.
2. **Snapshot** of `current_location` and per-quest `status` taken for heuristic plot-point detection.
3. **`PromptOrchestrator.build_payload`** assembles the three-tier memory context (see below) plus a system message containing world rules and the structured-output spec.
4. **`AIClient.generate_narrative`** posts to GitHub Models with `response_format=json_object`.
5. **`ai/parser.parse_response`** parses the JSON. On malformed output it falls back to treating the raw text as narrative and emits a `parse_warnings` entry.
6. **`engine.state_changes.apply_changes`** dispatches each `{op, ...}` entry through a typed handler. Unknown ops, malformed payloads, and out-of-range values are dropped with a description rather than crashing the turn.
7. **PlotPoint recording** — if the LLM included a `plot_point`, it's appended to `story_history`. Heuristic backups also fire on detected location changes and quest status transitions, even if the LLM omitted them.
8. **UI render** — narrative + dim per-line `state_changes` summary + any parse warnings.
9. **Background summary** — if `turn_count - summary_anchor_turn ≥ SUMMARY_REFRESH_TURNS` (default 8), a Textual worker calls `AIClient.summarize` to roll the prior summary forward with the last 16 log lines, replacing `state.session_summary`. This runs concurrently with the next turn.

## Three-Tier Memory Model

The orchestrator builds the LLM context from three layers, in increasing token cost and decreasing temporal proximity:

| Tier | Source | What it covers | Refresh |
|---|---|---|---|
| **Hot** | `state.log[-6:]` | Verbatim last 6 PLAYER/NARRATOR lines. | Every turn (free). |
| **Warm** | `state.session_summary` | One-paragraph rolling summary of the session. | Background LLM call every `SUMMARY_REFRESH_TURNS` turns; covers the gap between hot and cold. |
| **Cold** | `state.story_history` (`PlotPoint`s) | Tagged significant events. The orchestrator always includes the last 3, plus tag-fuzzy-matched older points whose tags overlap with the current input or location. | Appended whenever the LLM emits `plot_point` or a heuristic fires (location change, quest status change). |

Recall matching is keyword-based with light stopword filtering and tokenization on both `tags` and `event` text — not embeddings. Capped at 5 deep-recall hits per turn.

## Structured LLM Output

The system prompt requires the LLM to return a single JSON object:

```json
{
  "narrative": "<player-facing prose>",
  "state_changes": [{"op": "...", ...}, ...],
  "plot_point": {"event": "...", "choice_made": "...", "tags": ["..."]} | null
}
```

`narrative` is the only text the player sees. `state_changes` mutate `GameState` deterministically — ops are defined and validated in `engine/state_changes.py`:

| Op | Effect |
|---|---|
| `add_item` / `remove_item` | Inventory mutation. |
| `damage_player` / `heal_player` | HP delta, clamped 0..max_hp. |
| `adjust_resonance` | Bloodline resonance delta. |
| `move_to` | Set `current_location`. Auto-creates the location if unknown. |
| `discover_location` | Add or enrich a `Location` (description, connections). |
| `set_time_of_day` / `set_weather` / `set_world_flag` | World state. |
| `advance_quest` / `complete_quest` / `fail_quest` | Quest progression. |
| `add_npc` | NPC roster (key = lowercased+underscored name). |

The full op reference is exported as `OP_REFERENCE` (in `engine/state_changes.py`) and injected into the system prompt by the orchestrator. **When adding a new op, register it in both `_HANDLERS` and `OP_REFERENCE`** so the model knows it exists.

The engine never trusts the LLM blindly: each handler validates types and ranges, and exceptions are caught per-op so a bad change doesn't kill the turn.

## Save Format

`GameState.save_to_file` writes to `<filename>.tmp` and uses `os.replace` for an atomic swap — no half-written saves on crash. `GameState.from_json` checks `schema_version` (currently **2**) and raises `IncompatibleSaveError` on mismatch. The pre-v2 `savegame.json` shipped with the repo is incompatible and will be refused with a clear message; delete it to start a new chronicle.

When evolving the schema:
1. Bump `CURRENT_SCHEMA_VERSION` in `engine/models.py`.
2. Either reject old saves (current behaviour) or add a migration branch in `from_json`.

## Module Map

| Module | Responsibility |
|---|---|
| `engine/models.py` | Dataclasses, JSON serialization, atomic save, schema-version check, `IncompatibleSaveError`. `GameState` is the single source of truth. |
| `engine/state_changes.py` | LLM-op dispatch + handlers + `OP_REFERENCE`. The boundary where the LLM is allowed to mutate state. |
| `engine/core.py` | `GameEngine` — holds the active state, loads quests, save/load entry points. |
| `engine/exploration.py` | Slice A helpers (mostly superseded by `move_to` op now). |
| `engine/combat.py` | Slice B (CombatManager — currently a stub). |
| `ai/client.py` | Async httpx client. `generate_narrative` (json_mode) and `summarize` (plain prose). |
| `ai/parser.py` | `parse_response` — robust JSON parsing with malformed-output fallback. |
| `ai/orchestrator.py` | `build_payload` — three-tier memory assembly + system-prompt construction. Tag tokenizer for cold-recall matching. |
| `ui/app.py` | `ChronosApp` (Textual) — turn loop, state-change application, plot-point recording, background summary worker, save/load actions. |
| `prompts/system_prompt.json` | Narrator persona, world rules, output_format spec. |
| `data/quests/*.json` | Data-driven quest definitions; `narrative_guidelines` is forwarded to the LLM as `quest.metadata.guidelines`. |

## Slice Division

- **Slice A (Exploration):** `engine/exploration.py`, world-state ops, NPC dialogue. Most movement now flows through `move_to` / `discover_location` ops.
- **Slice B (Combat):** `engine/combat.py`, HP/damage/dice math. Currently stubbed; integration with combat-specific prompts is a future task.

## Coding Constraints

- **UI/Logic separation:** Textual widgets handle rendering and events only. Game logic lives in `GameEngine`, the state-change handlers, or future managers.
- **Async:** All LLM calls and heavy processing must be `async`/`await`. Background tasks run via `App.run_worker`. Never block the Textual event loop.
- **Type safety:** Dataclasses + explicit `typing` annotations for domain objects. No untyped dicts crossing module boundaries except for the LLM-payload shape (which is parsed and validated at the boundary).
- **State mutation contract:** Anything the LLM might want to change must go through a registered op in `engine/state_changes.py`. Direct mutation of `state.*` from the UI is allowed only for engine-driven mechanics (e.g., `turn_count`) and dev-only paths (potion action).
- **Defensive parsing only at the LLM boundary.** Internal callers (engine ↔ UI) trust each other and use plain dataclass calls.

## Tunables

These constants are at module top of `ui/app.py` and `ai/orchestrator.py`:

- `SUMMARY_REFRESH_TURNS = 8` — how often the warm-tier summary is rebuilt.
- `SUMMARY_INPUT_LOG_LINES = 16` — log slice fed to the summarizer.
- `_RECENT_LOG_LINES = 6` — hot-tier window in the prompt.
- `_BACKGROUND_PLOT_POINTS = 3` — number of latest PlotPoints always included.
- `_MAX_DEEP_RECALL = 5` — cap on tag-matched older PlotPoints per turn.
